# NDOS boot from a mounted MAME SD image

The reduced MAME J68K driver exposes a writable, removable raw-image device named `sdcard`. It accepts `.img`, `.ima`, and `.raw` images whose non-zero length is a multiple of 512 bytes. The project build creates `build/disks/ndos-sd.img`, a standard 1.44 MiB FAT12 image containing `NDOS.SYS` and the generated NEX applications.

`Run-NDOS.cmd` mounts `disk/j68k/sdcard.img` using `-sdcard`. On first launch, `tools/sdcard_manager.py --prepare` copies in the generated image and leaves an existing card untouched. If you rebuild NDOS and want to keep the other files on your live card, close MAME and run `Update-NDOS-on-SD.cmd`; it backs up the full image and replaces only root `NDOS.SYS`. `Install-SD-Card.cmd` remains available when you intentionally want to replace the entire live card with the generated image. The launcher prints a reminder when it preserves an existing image. The mounted card is writable; changes go directly into its image file.

The normal `Run-NDOS.cmd` launcher enables MAME's UI input, so **Tab** should open the internal UI without starting the debugger. Choose **File Manager**, select **sdcard**, then choose **[empty]** to eject it or select a different `.img`, `.ima`, or `.raw` file to insert one. The status and sector-count registers update immediately, and NDOS uses the RAM-disk fallback while no card is inserted. MAME owns an open image, so do not edit or overwrite that file from Windows until you eject it in MAME or close the emulator. You can also choose a card at launch with `-sdcard "path\\to\\card.img"`.

Tab/File Manager swaps whole disk-image files; it does not copy a PC file into the FAT filesystem inside the card. To copy a PC file onto the persistent SD image, close MAME and run `Import-File-to-SD.cmd`. It opens the file picker and uses the source filename as the FAT 8.3 destination. You can also drag in a source path from a terminal, or provide an explicit name: `Import-File-to-SD.cmd "C:\\path\\MYFILE.TXT" MYFILE.TXT`. This preserves existing files and refuses to overwrite a duplicate name. Start MAME again; `MOUNT` should report the SD card, and `DIR`, `TYPE filename.ext`, and `RUN program.nex` will search that card's root directory.

The BIOS still runs the reset alias, POST, and one-way overlay clear as before. It then looks for the exact root-directory 8.3 entry `NDOS    SYS` in the mounted card's FAT12 volume, follows its cluster chain, copies the file to physical address zero, checks its initial SSP/PC, and jumps to the NDOS reset entry. If no card is mounted, the BPB is unsupported, or the file cannot be loaded, it copies the embedded ROM copy of `NDOS.SYS` and boots that instead.

When MAME reports an SD card present, NDOS's FAT12 block-device adapter routes filesystem calls to that card. `DIR`, `TYPE`, `RUN`, `WRITE`/file creation, `DELETE`, `ATTRIB`, `FATINFO`, and `FREE` use the SD volume. With no card mounted, those calls fall back to the existing 512 KiB FAT12 RAM disk. `MOUNT` validates and reports the active FAT12 volume. Bare `FORMAT` still targets only the RAM disk; `FORMAT SD` explicitly targets the inserted SD card and requires a separate `YES` confirmation. The FAT12 layer remains media-independent, and the MAME sector adapter is isolated in `c/platform/ndos_block.c`.

The BIOS and current NDOS filesystem adapter support 512-byte sectors, a FAT12 volume with a fixed root directory, root-level files, and a BIOS-loaded NDOS image no larger than 64 KiB. FAT16, subdirectories, partition tables, SD protocol timing, and actual SPI signals are not implemented. MAME insert/eject only simulates media changes; it does not prove physical SD hot-plug electrical behavior. The MAME register block at `$00E30000` and sector buffer at `$00E31000` are temporary emulator interfaces, not a frozen CPLD2 or physical SD-card ABI. The older 512 KiB FAT12 RAM disk remains available as the no-card fallback and as the separate `FORMAT` target.

Automated checks are `luatests/test-sd-boot.lua` (card boot, immutable NDOS code comparison, and CPU reaching the shell's DUART input wait after the prompt), `luatests/test-sd-fallback.lua` (the same shell-ready check through ROM fallback with no card), `luatests/test-sd-write.lua` (single-sector card write/read), and `tools/test_sd_runtime.py` (NDOS mount selection, root enumeration, and reading an imported file from an isolated SD image). The runtime test copies the generated image to `build/test-results/sd-runtime.img`; it does not modify the live development image. The shell-ready check is paired with the saved terminal screenshot because the CPU-state check alone cannot prove what was rendered on screen.
